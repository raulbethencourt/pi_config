**Done.** Landed as the `rules-loader` extension (`agent/extensions/rules-loader/`), hooking `tool_result` for `read`/`write`/`edit` calls and merging global (`~/.pi/agent/rules/*.md`) with project-local (`<project>/.pi/rules/*.md`, using pi's own `CONFIG_DIR_NAME` convention rather than Claude's `.claude/rules`) rule files, project taking precedence on same-basename collisions. ### 10. Shared task list + file-locking for parallel multi-agent delegation — done
Claude Code's experimental "Agent Teams" feature adds a shared, dependency-tracked task list, peer-to-peer teammate messaging, and file locking to prevent merge conflicts between parallel sessions. Pi's roster-based delegation model implies parallel multi-agent runs but doesn't coordinate around shared state today. Even a lightweight version (a shared JSON task list + a per-file claim/lock) would reduce collision risk.

**Done.** New extension at `agent/extensions/coordination/` (`session-dir.ts`, `lock-store.ts`, `tasks.ts`, `index.ts`) gives sibling subagents dispatched from the same top-level `pi` process a shared per-file lock and a shared `tasks.json`. `session-dir.ts` resolves `~/.pi/agent/state/coordination/<sessionId>/` (sessionId = `<pid>-<timestamp>`) and canonicalizes paths (symlink-resolved, with a not-yet-existing-write-target fallback) so lock keys are stable across equivalent path strings. `lock-store.ts` is the actual mutual-exclusion primitive: atomic on-disk exclusive creation (`fs.promises.open(lockPath, "wx")`, the only mechanism visible across separate OS processes) layered with an in-process reentrancy map so repeated acquisitions by the same pid are free. Reap model is dead-pid-only, no TTL ever — a lock is reclaimed only when `process.kill(holderPid, 0)` throws `ESRCH`, never based on file age or elapsed time; this was a deliberate correction after an initial critic BLOCK on an earlier TTL-based reaping design. `index.ts`'s `acquireLocksForPaths` sorts a multi-file tool call's target canonical paths lexicographically before acquiring (a fixed global order across every caller, preventing cross-call deadlocks) and rolls back every already-acquired lock if any later acquisition in the sequence fails after its retry/backoff budget — no partial lock state is ever left behind. A shared `agent/extensions/shared/hashline-paths.ts` module was extracted during this work, deduplicating path-normalization logic that had drifted into a third near-identical copy across `hashline` and `rules-loader` (a duplication smell this work incidentally fixed rather than introduced). The extension is deliberately loaded only into subagent child processes, never the interactive main session: `agent-loop.js` skips `finalizeExecutedToolCall`/`afterToolCall` for a blocked `tool_call`, so a blocked call never produces a matching `tool_result` — if some other extension's handler blocked a call after this one had already granted a lock earlier in the same handler chain, the lock would leak permanently (recoverable only once the holding process itself dies); restricting to subagent children, whose only other co-resident hook is `hashline`'s `tool_result`-only handler, sidesteps this entirely. Wired into both `agent/extensions/subagents/index.ts` (the interactive dispatch path) and `agent/extensions/subagents/build-args.ts` (the standalone/mcp-server reuse path), each minting its own coordination session id via a shared `mintCoordinationSessionId()` helper and threading it to spawned children via `PI_COORDINATION_SESSION_ID`. Covered by 24 new coordination tests (`agent/tests/coordination-{lock-store,multi-file-atomic,stale-session-prune,tasks}.test.ts`, including a real-SIGKILL regression test and an explicit no-TTL regression test) plus the pre-existing suite with no regressions. Passed a two-stage code review with a final APPROVE (0 Critical, 0 Important); its cheap advisory follow-ups were folded back in immediately after: narrowing the dead-pid liveness check in `lock-store.ts`/`session-dir.ts` to only treat `ESRCH` as dead (any other error, e.g. `EPERM`, now logs and falls through to the safe "assume alive" default rather than being treated as dead), and documenting one more accepted limitation in the README. Explicitly out-of-scope for this v1: no cross-session protection (two separate top-level `pi` invocations get independent coordination directories with no shared visibility), no guarantee on network filesystems (NFS/SMB — the design assumes `~/.pi` is on local disk), no read-consistency guarantee, and — newly documented — two concurrent tool calls (different `toolCallId`s) from the *same* subagent process targeting the same file are both granted rather than serialized, since the in-process reentrancy map keys only on pid and pi-agent-core executes a turn's prepared tool-call bodies concurrently by default (blocking would deadlock the batch); this is not a regression, since baseline pi has the identical race with no coordination extension at all, and it stays outside this extension's "separate OS processes" threat model.

### 19. `Prompt Suggestions`-style ghost-text next-message hint — done
Claude Code shows a grayed-out suggested next message directly in the prompt input bar after each response — accepted with Tab/Right-arrow (fills the input box, then Enter sends it) or dismissed by just typing. On a session's first turn it's seeded from git history (recently-worked files); afterward it's derived from conversation context (e.g. suggesting "commit these changes" right after an implementation finishes). It runs as a low-cost background request reusing the parent conversation's prompt cache, is skipped in plan mode and by default in print/non-interactive mode, and is toggleable via `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false` or `/config`. No equivalent found in pi's inventory: `zsh-history.ts` (ctrl+r) is a manually-invoked picker over shell history, not an automatic post-response hint, and `pi-tui`'s `AutocompleteProvider` mechanism is trigger-character-driven completion for `@`-mentions/paths/slash-commands while typing, not an idle full-message suggestion offered after the agent finishes. Porting this needs a materially different TUI primitive (ghost text rendered in the empty input box, accepted on Tab/Right-arrow, cleared on first keystroke) plus a background low-cost suggestion request keyed off turn-end and, for the first turn, `git log`/`git diff` of recently-touched files — more than a small addition to the existing autocomplete/history surface, so scope it as its own item.

**Done.** New extension at `agent/extensions/ghost-suggest/` implementing ghost-text prompt suggestions in the input box, structured as: `guards.ts` (pure eligibility + first-turn-detection logic, unit-tested), `generate.ts` (pure prompt-building + sanitization logic, unit-tested, plus git-log-fetching helper and cached background-LLM-request function reusing `btw.ts`'s side-session pattern), `editor.ts` (CustomEditor subclass rendering ghost text and intercepting Tab/Right-arrow-to-accept, approved under Legacy Code Exemption with manual checklist + scoped tsc typecheck due to tightly-coupled TUI code), and `index.ts` (wires extension via `agent_end` hook). Underwent full planner→critic review cycle with a genuine revision loop: first critic pass flagged a fabricated-looking `ctx.mode` field claim, which a second evidence-based pass confirmed actually exists in the installed `@earendil-works/pi-coding-agent` package — demonstrating the review process catching and correctly resolving a real ambiguity rather than a defect. Implementation incidentally discovered a pre-existing dormant bug in `agent/extensions/btw.ts` (~line 554): a `session.agent.replaceMessages(...)` call referencing a method that doesn't exist on the installed Agent class, never triggered by any current test but worth a follow-up investigation. Test results: `guards.test.ts` and `generate.test.ts` both fully GREEN (24 + 14 tests respectively), plus a new `agent-state-messages.test.ts` (3 tests); full suite 878 passing with identical 7 pre-existing unrelated failures as baseline (tests/token-stats-*.test.ts, tests/powerline-subagents.test.ts), confirmed via git stash comparison to predate this work. `agent/vitest.config.ts`'s `include` glob was broadened to also discover `extensions/**/*.test.ts` so co-located tests run under the standard test command. Code-reviewer approved with HIGH confidence, zero blocking findings; one advisory note (not a defect): git commit metadata including author emails is sent to the LLM in the first-turn seed prompt — inherent to the approved design and worth documenting for maintainers. ## Backlog (found during item #6's review process)

### 15. `bash-guard`: `find`/`fd` bypass protected-path blocking entirely via bare command-name matching — fixed
`READ_ONLY_CMDS` (in `agent/extensions/bash-guard/index.ts`) classifies any command starting with `find` or `fd` as unconditionally read-only via a bare command-name prefix match, with no inspection of the command's own arguments. `analyzeSegment`'s general risk-scoring path does separately flag `find <path> -delete` as high severity — but that's an independent, best-effort warning-and-prompt mechanism, not the same code path as the protected-path hard-block. For the protected-path hard-block specifically (`findBlockedProtectedFolderReference`, and the analogous `PROTECTED_WRITE_ONLY_FILES`/`PROTECTED_PATH_PATTERNS` check right after it), matching on the bare command name means `find <protected-path> -delete` or `find <protected-path> -exec rm {} \;` is still classified read-only and sails straight through the hard-block, for every `PROTECTED_FOLDER_ENTRIES` entry (old directory entries and the newer credential-file entries alike) — not something narrow to this session's additions. Found while reviewing/fixing the narrower read-only-exemption bug for the two credential-file entries (item #6); deferred as its own dedicated fix given the severity (full bypass of the hard-block, not just a downgrade to a promptable warning) and breadth (affects the entire `PROTECTED_FOLDER_ENTRIES`/`PROTECTED_WRITE_ONLY_FILES` surface, not one entry). Likely fix shape: give `find`/`fd` the same segment-level argument inspection `analyzeSegment` already does for `find -delete`, but wired into the protected-path block path rather than only the general risk-prompt path — e.g. only treat `find`/`fd` as read-only when none of `-delete`, `-exec`, `-execdir`, `-fprintf`, `-ok`, `-okdir` appear among its arguments.

**Fixed.** The bare command-name misclassification described above is closed, and review of the fix surfaced (and closed) several further bypasses of the same protected-path hard-block along the way: chaining (`&&`, `;`, `||`), piping (`|`), backgrounding (`&`), `;;`, `|&`, bare newlines, and `fd`'s bundled short-flags (`-Hx`-style, where a value-taking flag character bundled into a short-flag group was previously invisible to the exemption check). Fix lives in `agent/extensions/bash-guard/index.ts`, with regression coverage in `agent/tests/bash-guard-protected-paths.test.ts` (133 bash-guard-related tests passing).

### 16. `bash-guard`: command/process substitution still bypasses the protected-path hard-block
Command substitution (`$(...)`, backticks) and process substitution (`<(...)`, `>(...)`) still bypass the same protected-path hard-block fixed in item #15, because `shell-quote` flattens a substitution's inner tokens into the same segment as the outer command with no nesting-depth marker — e.g. `cat $(rm -rf ~/.ssh)` is still misclassified as read-only, since `cat` reads as the (only visible) command. Fixing this needs subshell-depth-aware tokenization, which is a materially larger change than the fixes already applied in item #15. This gap is documented inline in `agent/extensions/bash-guard/index.ts` near the `splitOnOps` call site.

**Fixed.** The substitution-bypass gap is closed via a new raw-string scanner `extractSubstitutionSpans()` in `agent/extensions/bash-guard/index.ts`, which directly scans for all four substitution forms (`$()`, backticks, `<()`, `>()`) without relying on `shell-quote`'s token boundaries. `isReadOnlyBashCommand()` now unconditionally disqualifies any command containing detected substitution syntax from the read-only exemption (fail-closed design: even harmless inner content like `cat <(cat ~/.ssh/config)` loses the exemption if a protected path is textually referenced anywhere). Separately, `analyzeBashCommand()` (the general risk-scoring path, distinct from the hard-block) gained depth-capped (max depth 5) recursive scanning into each substitution span, merging severity and attaching "inside command/process substitution: " prefix so dangerous commands hidden in substitutions still surface as risk prompts rather than silently passing. Two intentional over-detection trade-offs are documented inline: the scanner doesn't track quoting (a quoted literal containing `$(text)` still registers as substitution), and `$((...))` arithmetic expansion also registers (stronger conservative stance than attempting to distinguish it from command substitution). Covered by 17 new regression tests across `agent/tests/bash-guard-protected-paths.test.ts` and `bash-guard.test.ts`, testing all four bypass forms, a credential-file variant, a should-not-false-positive case, the confirmed fail-closed trade-off, a malformed/unterminated-input case, and a depth-cap/no-hang case. Underwent scout→planner→critic review (critic raised a REVISE on unconditional fail-closed scope, resolved via explicit user confirmation to keep it); then worker→code-reviewer pass (APPROVE, HIGH confidence, zero Critical/Important findings). Full test suite: 159/159 passing in bash-guard test files, 898/905 in full suite (7 pre-existing unrelated failures).

### 17. `bash-guard`: `fd` bundled-short-flag value-taking set is missing two real value-taking flags
The bundled-short-flag detection added while fixing item #15 defines its value-taking-flag set as `FD_VALUE_TAKING_SHORT_FLAG_CHARS = new Set(["d", "E", "t", "e", "S", "c", "j"])` in `agent/extensions/bash-guard/index.ts`, but `fd` has two more real value-taking short flags not in that set: `-o`/`--owner` and `-C`/`--base-directory`. This can only cause rare over-blocking (a harmless `fd` invocation being incorrectly treated as non-exempt from the read-only classification), never a new bypass, so it's low priority — but worth completing the set for correctness.

### 18. `bash-guard`: output redirection to a protected path is not hard-blocked in headless/subagent mode
`analyzeBashCommand` in `agent/extensions/bash-guard/index.ts` flags output redirection (`>`, `>>`, `2>`) as a promptable "medium" risk, but that's a UI confirmation prompt, not the protected-path hard block (`findBlockedProtectedFolderReference`/`PROTECTED_WRITE_ONLY_FILES`/`PROTECTED_PATH_PATTERNS`) fixed in items #15–#17 — `tokensToStrings` strips redirect operators without them ever disqualifying a command from the read-only exemption there. Worse, the promptable path itself is skipped entirely in headless/non-interactive execution when `bash-guard-auto-allow` is set (the common subagent execution path), since `promptRunOrAbort` short-circuits before ever reaching the user. Net effect: a command like `cat payload > ~/.ssh/authorized_keys` (or `echo ... >> ~/.ssh/authorized_keys`) run by a subagent in headless mode is neither prompted nor hard-blocked, and can silently overwrite a protected path. This is a **pre-existing gap, not a regression** — the old bare-regex classifier that items #15–#17 replaced had the identical hole, since it never inspected redirect targets either. Deferred as its own item given it needs a materially different fix shape (teaching the protected-path hard-block to inspect redirect targets, independent of the read-only/mutating-primary classification those items addressed) rather than a small addition to existing logic.
